# 評価設計

## 1. 何を測るか

MVP 段階では retrieval を主評価対象にする。

- Top1 Hit Rate
- Top3 Hit Rate
- Recall

ここで言う `Hit` は、期待する資料または期待するチャンクが上位候補に入ること。

## 2. なぜ生成品質を主評価にしないか

このテーマでは、回答文の流暢さよりも以下が支配的だから。

- 欲しい手順書が引けるか
- 古い手順ではなく更新版が優先されるか
- 根拠ファイルを辿れるか

つまり、生成品質より retrieval 品質が先行指標になる。

## 3. 評価データの考え方

- 想定問い合わせを `question`
- 正解候補文書を `expected_sources`
- 補助的に `expected_terms`

として持つ。

例:

```json
{
  "question": "CAN通信異常時の確認項目は？",
  "expected_sources": ["can_troubleshooting.md"],
  "expected_terms": ["終端抵抗", "配線", "ボーレート"]
}
```

## 4. 見せたいこと

- 単に LLM を載せたのではなく、検索評価を分離して設計していること
- 業務課題に対して、検索可能状態の整備を主因として扱っていること
- 後で Embedding を追加しても比較可能な形になっていること
