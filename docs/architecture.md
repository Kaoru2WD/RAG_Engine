# アーキテクチャ

## 1. 設計原則

この再構築で守る原則は以下。

1. まず「検索できる状態」を作る
2. AI を使う前に、文書とメタデータの整備を重視する
3. 軽量で説明可能な検索経路を先に成立させる
4. 会社依存の接続先や機密データを、再現用コードから切り離す

このため、第一段階では SQLite FTS5 を主軸に置く。VectorDB を先に入れないのは、検索失敗の主要因が埋め込み品質ではなく、文書の粒度・命名・更新管理・抽出品質にあることが多いため。

## 2. システム境界

```text
Document Source
    ├─ SharePoint mirror
    ├─ PDF
    ├─ Word
    ├─ Excel
    ├─ HTML
    └─ Markdown
         ↓
Extractor
         ↓
Chunker
         ↓
SQLite FTS Index
         ↓
Retriever
         ↓
Answer Composer
         ↓
FastAPI
```

## 3. コンポーネント責務

### Source Sync

- 実務では SharePoint から定期同期
- ポートフォリオではローカルフォルダ同期に置換
- ここは `ingest 元の調達` に限る

### Extractor

- 拡張子ごとにテキスト抽出
- 抽出不能時は黙殺せず、エラー理由を残す
- 抽出品質のばらつきが retrieval 劣化要因になるため、ここは運用上の重要点

### Chunker

- 500〜1000 文字程度を基本とした固定長チャンク
- オーバーラップは 100 文字を標準とする
- セクション見出しが取れる場合はメタデータとして保持する

### Index

- SQLite FTS5 にチャンク本文とメタデータを登録
- `bm25()` によりスコアリング
- チャンク原文と出典ファイルを返せるようにする

### Answer Composer

- 現段階では retrieval 結果を根拠付きで整形
- LLM を使う場合でも、検索結果を先に固定し、回答は後段責務に限定
- 「AI が自動判断した」ように見せない

## 4. 将来拡張の切り方

### Embedding 追加

- 再ランキングまたはハイブリッド検索として追加
- 既存 FTS を消さずに併存させる

### SharePoint 実接続

- 認証・同期・差分管理を `sync` 層へ閉じ込める
- portfolio 版ではスタブのままにし、機密接続情報を不要にする

### Human-In-The-Loop

- 低信頼回答時に「関連資料候補」と「不足情報」を提示
- 自動決定ではなく、人間の運用判断ポイントを明示

## 5. 技術選定理由

### なぜ FastAPI か

- 検索 API と ingest API を素直に分けられる
- 後で UI や評価バッチからも叩きやすい

### なぜ SQLite FTS5 か

- 単一ファイルで持ち運べる
- 初期セットアップが軽い
- スコア経路が比較的説明しやすい

### なぜ最初から Chroma / FAISS にしないか

- 「ベクトル化したのに欲しい資料が出ない」問題の多くは、抽出・分割・命名・更新管理の問題だから
- 先にそこを見える化しないと、RAG の説明責任が曖昧になる
